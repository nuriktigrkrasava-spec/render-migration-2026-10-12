# Перенос для принимающего специалиста

## До переключения

Сверить `render/services.json` с Dashboard; снять отдельные резервные копии каждого хранилища. Проверить восстановления на закрытом тестовом сервере. Конфигурация собрана через API, сами production-базы не скачивались и не менялись.

### SQLite: iiko и iiko-demo

Это разные сервисы с разными persistent disks. Прочитать настоящий DB_PATH из Environment каждого сервиса; он не обязательно одинаков. Сделать согласованную копию штатным SQLite backup API / `.backup`, а не копированием одного файла активной WAL-базы. Перенести также вложения и остальные нужные файлы `/data`, если они есть. Проверить integrity_check, foreign_key_check, количество записей и возможность расшифровать сохранённые credentials прежним ENCRYPTION_KEY. Тестовая копия не должна отправлять сообщения реальным пользователям или собирать данные реальных клиентов.

При сохранении SQLite: один записывающий web-процесс, постоянный том, отдельный файл на каждый сервис, права только сервисному пользователю. При переходе на PostgreSQL: требуется перенос схемы, данных и слоя database.py, SQLite SQL/PRAGMA, транзакций, ID и типов. Простая установка DATABASE_URL в этом проекте не переводит его на PostgreSQL. Сначала адаптация на отдельной ветке, контрактные тесты, контроль связей и сверка денег/количеств.

### PostgreSQL: saya-kds

Использовать PostgreSQL 16-совместимые pg_dump/pg_restore, зашифрованную доставку дампа и новый закрытый пароль. В приложении DATABASE_URL имеет схему `postgresql+asyncpg://`. Точную строку и пароли не включать в этот репозиторий. Проверить create_all/добавочные миграции в backend/app/main.py; на первом тестовом старте не включать реальные pollers, reports и webhook registration. Проверить заказ, изменения статуса, Socket.IO, кухню, курьера и отчёты; перед переключением остановить старые фоновые задачи.

### Supabase: reading-platform

SQL миграции лежат в source/reading-platform/supabase/migrations. Перенести не только строки таблиц, но и RLS, функции/расширения, права; проверить дополнительные Storage/Auth ресурсы в самой консоли Supabase — Render API не показывает их содержимое и страну хранения. Подробная официальная процедура: https://supabase.com/docs/guides/platform/migrating-within-supabase/backup-restore . Если выбран обычный PostgreSQL вместо Supabase, текущий клиент @supabase/supabase-js и серверные вызовы придётся адаптировать либо развернуть совместимые Supabase сервисы.

## Переключение

Запустить новую среду без исходящих реальных уведомлений. Проверить права разных ресторанов/филиалов, вход по ссылке, HTTPS, денежные суммы, операции с документами, очередь/повторы, webhooks и загрузки. Согласовать окно остановки записи; сделать финальные согласованные резервные копии; остановить старые фоновые обработчики; восстановить данные; обновить домены, webhooks, связи iiko→KDS и мобильные API_URL. Старые пользовательские личные ссылки могут содержать onrender.com: нужны безопасные redirects/новые ссылки и проверка нативных deep links.

## Откат

Не удалять старые сервисы, тома или базы до приёмки. Сохранять точку восстановления и прежнюю конфигурацию. После возникновения новых записей на новом сервере нельзя просто вернуть старую базу без плана согласования изменений: это потеряет новые заказы/документы. Копии и ключи передавать только закрыто. По завершении отозвать выданные токены GitHub/Render и удалить временные доступы.
